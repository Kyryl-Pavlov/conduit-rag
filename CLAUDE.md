# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Conduit RAG: an LLM-agnostic RAG (retrieval-augmented generation) system. Users upload text, PDF, audio, or video files through a Next.js frontend; an SQS-chained (and, for audio/video, asynchronously-continued) pipeline of AWS Lambdas partitions, embeds, and indexes them into a pgvector-backed Aurora Postgres store for retrieval.

### Local end-to-end stack (docker-compose emulators)

```bash
cd infra/local
docker compose up -d --build   # postgres+pgvector, dynamodb-local, minio (S3), elasticmq (SQS), frontend, dispatcher/worker/db-writer pollers
```

No `transcribe_completion` poller exists locally: `TRANSCRIPTION_PROVIDER=fake` (set on `dispatcher` in docker-compose) fabricates a transcript synchronously inside `dispatcher` itself, so that Lambda is exercised only by `pytest`, never by this stack. Same story, one tier further, for `video_completion`: `VIDEO_PROVIDER=fake` fabricates placeholder object detections synchronously inside `dispatcher`, so `video_completion` — and the Fargate task it would otherwise wait on — get **zero** local coverage at all, not even via `pytest` for the Fargate task's own code (see the Architecture section below).

Or exercise the same flow through the real UI at `http://localhost:3000` (upload → status polling; the frontend's own API routes talk to the same emulators).

## Architecture

### Pipeline: dispatcher → worker → db_writer

Three SQS-chained Lambdas process an uploaded file, each triggered by the previous one's output queue:

1. **dispatcher** (`src/dispatcher/handler.py`) — triggered by S3 `ObjectCreated` events delivered via the dispatch-queue. Splits the file into a fixed **10-way byte-range partition fan-out** (`common/chunking.compute_partitions`, bounds worst-case concurrency regardless of file size), creates the `file_status` DynamoDB record, and sends one `WorkerMessage` per partition to the worker-queue — this shared partition/create-file_status/fan-out tail lives in `common/fanout.fan_out_partitions` so `transcribe_completion` (below) can call the identical logic. For `.txt` uploads, file size comes straight off the S3 event and dispatcher never calls `HeadObject`/`GetObject`. `.pdf` uploads are the exception: dispatcher downloads the whole PDF, extracts its text (`common/pdf.extract_pdf_text`, pypdf-based, pure Python), and re-uploads the extracted plain text to `extracted/{file_id}.extracted` in the same bucket — `.extracted`, never `.txt`/`.pdf`, since either suffix would re-trigger the same S3 notification and double-dispatch the extraction output as a bogus independent upload. Partitioning then runs against that extracted text's byte length instead of the PDF's own size; `file_id`/`file_status.file_size_bytes` still reflect the original PDF throughout (chunk IDs, status display), so **worker and db_writer need no PDF-specific logic at all**. Audio uploads (`.mp3`/`.wav`/`.m4a`/`.flac`, see `common/transcription.AUDIO_EXTENSIONS`) are a third, structurally different exception, handled by `_dispatch_audio_upload`: transcription is an async job that can run minutes, so dispatcher can't extract-and-continue synchronously the way it does for PDF. `TRANSCRIPTION_PROVIDER=fake` (local dev) fabricates a placeholder transcript inline and fans out immediately, same shape as `.txt`/`.pdf`; `TRANSCRIPTION_PROVIDER=transcribe` (real) only starts the Transcribe job and returns — no `file_status` record exists yet, so the file is invisible in the frontend until `transcribe_completion` (below) picks up the finished job, an accepted limitation rather than a placeholder "transcribing" status. Video uploads (`.mp4`/`.mov`/`.webm`, see `common/video.VIDEO_EXTENSIONS`) are a fourth exception, handled by `_dispatch_video_upload`, structurally identical to audio's two-phase split but orchestrated differently: there's no managed AWS service for "detect objects/products in this video," so the real (non-fake) path runs a pluggable, provider-agnostic vision-LLM call (`common/video.VIDEO_PROVIDER=<name>|fake`, modeled on `EMBEDDINGS_PROVIDER`) on a Fargate task orchestrated by Step Functions (`infra/cloud/modules/video_pipeline`) instead of a managed job like Transcribe. `VIDEO_PROVIDER=fake` fabricates placeholder object-detection JSONL inline and fans out immediately, same shape as fake-mode audio; any other value starts a Step Functions execution and returns, deferring to `video_completion` (below) — but note only `fake` is actually implemented right now (`common/video.analyze_video` is a stub, see Current state below), so a real `terraform apply` with a real `VIDEO_PROVIDER` would currently fail inside the Fargate task. Permanently-invalid input (unsupported extension, empty file, oversized/textless PDF, oversized/empty audio/video, checked in `_resolve_worker_object`/`_dispatch_audio_upload`/`_dispatch_video_upload`) raises `DispatchValidationError`, which the handler catches to write a `status=failed` `file_status` record via `create_failed_file_status_record` instead of letting the exception propagate — these are non-retryable, so SQS's normal retry/DLQ handling (appropriate for transient errors) would otherwise just retry a doomed message forever while the file stays invisible to the frontend.
2. **worker** (`src/worker/handler.py`) — one invocation per partition. Fetches its byte range (plus a small overlap buffer for non-final partitions) from S3, then branches on `WorkerMessage.partition_format` (read via `.get()`, defaulted to `"text"`, so old in-flight messages from before this field existed still decode): `"text"` trims to clean whitespace boundaries (`common/chunking.trim_partition_bytes` — this is what keeps chunks from splitting mid-word across partition seams) and splits into overlapping token-window chunks (`chunk_text`); `"transcript"` (audio) and `"video"` (visual object/product detections) both trim to newline boundaries instead (`common/transcript_chunking.trim_transcript_partition_bytes`, since a JSONL line — not a byte — is the atomic unit) and pack whole JSONL segments into token-window chunks (`chunk_transcript_text`), contributing `start_time`/`end_time` into each chunk's metadata dict — identical wire shape, kept as distinct `PartitionFormat` values (and now stamped into `metadata["partition_format"]`) purely for provenance, since "a speaker said X" and "an object was visible" are different claims about the same timestamp range. Either way, each chunk is embedded via Bedrock Titan Text Embeddings V2 (`common/bedrock.embed_batch` — sequential `invoke_model` calls; there's no true multi-text batch API for synchronous invoke), and one `WriteMessage` per chunk goes to the write-queue.
3. **db_writer** (`src/db_writer/handler.py`) — batched (`batch_size=10`). Upserts each chunk into Aurora's `chunks` table (`common/vectordb.VectorDBClient`) and is the **only** thing that advances `file_status` (`chunks_written`, `completed_workers`, final `status=indexed`). This is the only Lambda that touches the `chunk_completion` table. `metadata` is a free-form `JSONB` column, so db_writer passes transcript/video chunks' `start_time`/`end_time`/`partition_format` through completely opaquely — no schema or code change was needed here for audio or video, only new keys in the dict worker already builds.
4. **transcribe_completion** (`src/transcribe_completion/handler.py`) — the async second half of real-mode audio dispatch. Triggered by an EventBridge rule on AWS Transcribe's job-state-change event (push-based, not SQS — the only SQS-pipeline Lambda invoked that way, so it gets an explicit `aws_lambda_function_event_invoke_config` retry policy instead of SQS's visibility-timeout/DLQ machinery). Recovers the original `file_id`/`s3_bucket` from tags dispatcher attached at `StartTranscriptionJob` time (`common/transcription.recover_upload_identity` — there's no `file_status` record yet at job-start to look them up in instead), collapses Transcribe's word-level output JSON into the same JSONL segment format the fake-mode path produces (`common/transcription.parse_transcript_json_to_jsonl`), stages it to `extracted/{file_id}.extracted`, and calls the same `fan_out_partitions` dispatcher uses. On a `FAILED` job, or a `COMPLETED` job with no recognized speech, it writes a failed `file_status` record instead.
5. **video_completion** (`src/video_completion/handler.py`) — the async second half of real-mode video dispatch. Invoked **directly** by the video-analysis Step Functions state machine (a plain dict payload, not an EventBridge/SQS envelope) once its Fargate task (`src/video_task/`, see Infra layout below) finishes — simpler than `transcribe_completion`: Step Functions already knows success/failure via its own `Catch`, and passes `file_id`/`s3_bucket` straight through as the execution's JSON input, so unlike `transcribe_completion` there's no tag-based identity recovery step. On `status: "SUCCEEDED"`, the Fargate task has already staged `extracted/{file_id}.extracted` (same JSONL shape as audio), so this Lambda just calls `fan_out_partitions` with `partition_format="video"`. On `status: "FAILED"`, it writes a failed `file_status` record instead.

**Idempotency is load-bearing throughout**, because SQS is at-least-once and every step must survive redelivery without double-counting or duplicating work:
- `chunk_id` is deterministic (`file_id_w{worker_index}_c{local_chunk_num}`, `common/chunking.make_chunk_id`), so a redelivered worker message reproduces identical chunk ids rather than new ones.
- `create_file_status_record` and `mark_chunk_completion` (`common/db.py`) are both conditional puts (`attribute_not_exists`) — the caller treats a failed condition as "already done, skip the rest of this handler," not an error.
- Completion tracking is per-partition, not per-chunk-index, because a partition's chunk count varies and SQS doesn't guarantee order: `worker` stamps `chunk_count`/`total_workers` into each chunk's metadata, and `db_writer` maintains a `chunks_written` map (`{worker_index: count}`) on the `file_status` item, only rolling up to `completed_workers`/`status=indexed` once a partition's count reaches its `chunk_count`.

### Dual-backend toggles (production vs. local emulator)

Four independent env-var toggles exist because AWS Bedrock, the RDS Data API, AWS Transcribe, and (in spirit) a real video-understanding provider have no local emulators:
- `EMBEDDINGS_PROVIDER=bedrock|fake` (`common/bedrock.py`) — `fake` returns deterministic hash-seeded vectors (retrieval-meaningless, but free/offline). Local docker-compose sets this on `worker`.
- `DB_MODE=data_api|psycopg` (`common/vectordb.py`, mirrored in `frontend/lib/vectordb.ts`) — production Aurora is reached via the RDS Data API (no VPC needed by any Lambda); local docker-compose's plain `pgvector/pgvector` container is reached via `psycopg`/`pg` over the normal wire protocol instead. Both backends run the same SQL against the same `chunks` table schema, which lives in **two places that must stay in sync**: `infra/local/postgres-init/002-schema.sql` and a `null_resource` in `infra/cloud/modules/aurora/main.tf`.
- `TRANSCRIPTION_PROVIDER=transcribe|fake` (`common/transcription.py`) — `fake` fabricates a small deterministic placeholder JSONL transcript inline in `dispatcher`, entirely skipping the real async job/EventBridge flow (there's no local Transcribe *or* EventBridge emulator, so unlike the other two toggles there is no way to run the "real" path locally at all). Local docker-compose sets this on `dispatcher`. The fake transcript is sized deliberately large (`_FAKE_SEGMENT_COUNT`) relative to the default 10-way partition fan-out — too small a fake transcript reliably reproduces the known gap described below on nearly every local upload, which was caught empirically while verifying this feature.
- `VIDEO_PROVIDER=<name>|fake` (`common/video.py`) — same shape as `EMBEDDINGS_PROVIDER`, but **inverted default polarity**: it defaults to `"fake"` (not a real-sounding name) because, unlike every other toggle here, no real backend is implemented at all yet — `common/video.analyze_video` is a `NotImplementedError` stub. `fake` fabricates placeholder object/product-detection JSONL inline in `dispatcher`, same local-dev shape as fake-mode audio (no Step Functions/ECS/Fargate emulator exists locally either). Local docker-compose sets this on `dispatcher`.

### Frontend (`frontend/`)

Next.js App Router API routes (`frontend/app/api/*`) call `@aws-sdk/*` directly — no Lambda in the request path for upload/status/files. `lib/aws-clients.ts` mirrors the Python side's env-driven, endpoint-override-aware client construction. One asymmetry to know about: the S3 client used for presigning upload URLs (`app/api/upload/route.ts`) must use a **browser-reachable** endpoint (`AWS_ENDPOINT_URL_S3_PUBLIC`) since the browser PUTs directly against the presigned URL, while every other AWS client (DynamoDB, SQS, and the server-side S3 delete path) uses the docker-network-internal endpoint (`AWS_ENDPOINT_URL_S3`, etc.) — see the comments in `lib/aws-clients.ts` and `docker-compose.yml`'s `frontend` service before changing either.

`app/api/query/route.ts` does real retrieval, following the same no-Lambda-in-the-request-path pattern as upload/status/files: `lib/bedrock.ts` embeds the query via real Bedrock (TS port of `common/bedrock.py`'s `embed_text`, same `AWS_BEDROCK_*` credential handling), `lib/vectordb.ts`'s `similaritySearch` runs the pgvector cosine-similarity query (same `DB_MODE` toggle as the Python side), and `lib/generation.ts` generates the answer via the Anthropic SDK directly using `ANTHROPIC_API_KEY` (not Bedrock — a deliberate LLM-agnostic split between the embedding model and the generation model). There is no `query_api` Lambda; retrieval never needed one. `lib/api.ts`'s `queryApi()` signature didn't need to change.

### Infra layout

`infra/` splits into `infra/cloud/` (Terraform: S3, SQS, DynamoDB, Aurora Serverless v2/pgvector, IAM, Lambda zip+layer packaging — one shared `common/` Lambda Layer, since dispatcher/worker/db_writer/transcribe_completion/video_completion need zero third-party deps beyond the runtime-provided `boto3` (AWS Transcribe and Step Functions, like RDS Data API, are plain `boto3` clients — no extra layer), plus a second layer just for dispatcher's `pypdf` dependency built via a `null_resource`/`local-exec` `pip install --target` — pypdf is pure Python, so no cross-compilation concern for Lambda's target architecture) and `infra/local/` (docker-compose emulator stack: MinIO/ElasticMQ/dynamodb-local/pgvector-Postgres, plus `scripts/run_*.py` wrappers that long-poll an SQS queue and invoke the real unmodified Lambda `handler(event, context)` — no code duplication between local and deployed Lambda targets). `transcribe_completion` is push-triggered by an `aws_cloudwatch_event_rule` on Transcribe job-state-change events, not an SQS-backed `aws_lambda_event_source_mapping` like the pipeline's core three — the only EventBridge-invoked Lambda in this repo, and there's no local stand-in for it at all (fake-mode audio never leaves `dispatcher`). `infra/cloud/modules/video_pipeline/` (Step Functions state machine, ECS cluster/task definition, ECR repo, a Secrets Manager placeholder for a future provider API key) is this repo's **first infra using compute inside the default VPC** — Aurora's `data.aws_vpc.default`/`data.aws_subnets.default` lookup (duplicated, not shared, into this new module — only two call sites exist, premature to extract a `network` module) was previously only used for a DB subnet group, never for anything that actually runs inside it. `video_completion` is invoked directly by that state machine (a native `arn:aws:states:::lambda:invoke` Task state, not EventBridge), and `lambda`'s dispatcher function hand-constructs the state machine's ARN from its deterministic name (`local.video_state_machine_arn` in `modules/lambda/main.tf`) rather than referencing `video_pipeline`'s output directly — the two modules would otherwise depend on each other's outputs, an unresolvable Terraform module cycle (same reasoning gave dispatcher's `states:StartExecution` IAM grant its own root-level resource in `infra/cloud/main.tf`, mirroring the pre-existing `aws_sqs_queue_policy.dispatch_from_s3` "lives at root to dodge a cycle" pattern). Terraform conventions (backend/bootstrap/module layout, tagging, IAM-per-Lambda) mirror the user's other boilerplate repos rather than being invented fresh.

## Current state / not yet built

Per the original design doc, this is a mid-build system. Built so far: `dispatcher`, `worker`, `db_writer`, `transcribe_completion`, `video_completion`, the full upload/status frontend flow, real query/retrieval (Bedrock embedding + pgvector search + Claude generation, all directly in the Next.js API route, no Lambda), `.txt` and `.pdf` ingestion (S3 notification filters on both suffixes; see the dispatcher entry above for the PDF text-extraction detour), timestamp-preserving audio ingestion (`.mp3`/`.wav`/`.m4a`/`.flac` via AWS Transcribe — see the dispatcher/worker/transcribe_completion entries above), fake-mode video ingestion (`.mp4`/`.mov`/`.webm` — see the dispatcher/worker/video_completion entries above), and the local dev stack. **Not yet built:** OCR/scanned-PDF support (text-layer extraction only — `common/pdf.extract_pdf_text` returns empty for image-only PDFs, which dispatcher now surfaces as a `status=failed` file rather than an uncaught exception), encrypted-PDF support, the `redrive` Lambda, a real on-failure destination for `transcribe_completion`'s async invocation (an explicit retry-count config exists, but no DLQ/alerting beyond that), query-side timestamp display for audio/video-sourced chunks (the data is in `metadata.start_time`/`end_time`/`partition_format` today; nothing in the frontend surfaces it yet), API Gateway/SNS, GitHub Actions CI, and a full structured-logging/metrics pass. **A real video-understanding provider** (`common/video.analyze_video` is a `NotImplementedError` stub — only `VIDEO_PROVIDER=fake` works) and, as a direct consequence, **the entire real (Step Functions/Fargate) video path is authored but has never run end-to-end**: `VIDEO_PROVIDER=fake` never reaches `src/video_task/` at all (dispatcher short-circuits synchronously before ever starting a Step Functions execution), so that container's code, the state machine's ASL, and the surrounding Terraform (`infra/cloud/modules/video_pipeline/`) are unverified against real AWS — `terraform apply` hasn't run, and no vision-LLM provider is wired up to test with regardless. Several implementation details there were written from documentation/training knowledge and are flagged `# ASSUMPTION, verify against real AWS` at the point of use: the exact boto3 exception name/behavior for `ExecutionAlreadyExists` on a duplicate Standard-workflow execution name; whether `ecs:runTask.sync` fails the state (triggering `Catch`) specifically on a nonzero container exit code, which is the entire status-reporting contract `src/video_task/main.py` relies on, vs. only on ECS-level stop reasons; the exact ARN/required actions for the AWS-managed `StepFunctionsGetEventsForECSTaskRule` EventBridge rule `ecs:runTask.sync` depends on internally; and default-VPC subnets' actual public routability in a real account (assumed, needed since Fargate has no NAT gateway to route through in this repo's networking). **Known gap:** a partition whose trimmed text is empty or whitespace-only (possible for very small files under the fixed 10-way fan-out, or a partition landing entirely in a run of blank lines) makes `worker` send zero `WriteMessage`s for that partition; `db_writer`'s per-partition completion tracking never learns that partition existed, so the file is stuck at `status=processing` forever with no error. A real fix needs a protocol change (worker signaling "partition done, zero chunks" some way db_writer can count) — flagged, not yet fixed. This gap is markedly easier to hit for the JSONL transcript path than for prose: a partition landing without a clean `\n` boundary discards its entire fragment as unparseable (caught in `common/transcript_chunking.parse_jsonl_segments`), whereas the prose path still salvages a word fragment in the same situation — confirmed empirically while building audio ingestion (see the `TRANSCRIPTION_PROVIDER` note above). Similarly, `db_writer`'s idempotency marker (`mark_chunk_completion`) is written *before* the `chunks_written`/`completed_workers`/`mark_file_indexed` cascade it gates, so a crash in that narrow window permanently undercounts a partition rather than retrying cleanly on redelivery — a real fix likely needs those writes combined into one DynamoDB transaction. **Known limitation, accepted rather than fixed:** a real-mode (`TRANSCRIPTION_PROVIDER=transcribe`) audio upload has no `file_status` record — and so is invisible in the frontend — for the full duration of transcription, since dispatcher can't create one until it knows the transcript's size; `transcribe_completion` creates it once the job finishes. A placeholder `"transcribing"` status was considered and deliberately not built (see the plan this was implemented from) — same tolerance already extended to the gaps above. Several `transcribe_completion`/EventBridge implementation details (the job-state-change event's exact JSON shape, the Transcribe job ARN format, tagging/duplicate-job-name exception behavior, IAM resource-level scoping for `transcribe:*`) were implemented from documentation/training knowledge rather than verified against a real deployment, since `terraform apply` hasn't been run — treat these as flagged assumptions, not verified facts, until checked against real AWS. None of the above is observed in normal use, but worth fixing/verifying before relying on this for anything beyond personal-scale testing. When picking this up, don't assume any of these exist without checking current source — this list reflects the last known state, not a guarantee.
